# User Preferences
- Communicates in Spanish (technical and conversational); expects responses in Spanish. Confidence: 0.95
- Uses formal, structured instruction style with explicit constraints and restrictions. Confidence: 0.9
- Prefers phased development with explicit gate-checks — wants confirmation before moving to the next phase. However, expects immediate execution of clear, action-oriented directives (e.g., "create this structure") without unnecessary confirmation gates. Confidence: 0.95
- Wants AI to strictly respect phase boundaries and not jump ahead (e.g., producing code when only architecture was requested). Confidence: 0.95
- Expects structured deliverables: directory trees, dependency matrices, tables, diagrams — not freeform prose. Confidence: 0.85
- Strong preference for Clean Architecture with strict layer separation (shared/domain, frontend, backend, database). Confidence: 0.9
- Wants Clean Architecture with strict layer separation, but use cases live INSIDE each module (`modulo_*/shared/src/domain/usecases/`) to keep modules fully self-contained and composable. Rejects placing use cases in client systems (`sistemas_clientes/`). Modules should be complete building blocks — entities, repository interfaces, failures, AND use cases — so any system can be assembled by combining modules. Confidence: 0.9
- Enforces dependency rules through package boundaries — violations must be compile errors, not conventions. Confidence: 0.9
- Prefers multi-repo architecture: each system (ventas, gimnasio, etc.) lives in its own independent repository with its own backend. Modules are reused across repos, but each system is a fully isolated, standalone project — NOT a monorepo with shared backends. Confidence: 0.88
- Values unidirectional dependency flow toward the domain/shared layer; modules communicate only via abstract contracts. Confidence: 0.9
- Works on Windows (Flutter/Dart ecosystem). Confidence: 0.95
- Expects full-stack Dart: both frontend (Flutter) and backend server written in Dart. Considers Dart the natural/obvious choice for the backend layer — does not want to be told to use a different backend language or external service. Confidence: 0.85
- Expects full transparency about any file system operations — proactively asks what was created, modified, or deleted, and distrusts unsolicited changes. Confidence: 0.8
- Database-first workflow: provides raw SQL schemas as the starting specification for new modules, expects each layer to be derived from it progressively — SQL first, then other layers one at a time with approval. Confidence: 0.9
- Uses PostgreSQL as target database (pgcrypto, gen_random_uuid, plpgsql triggers). Confidence: 0.85
- Wants backend code to be database-agnostic — explicitly rejects DB-specific syntax (e.g. PostgreSQL `::float8` casts) in favor of portable solutions (e.g. Dart helper functions) that work across PostgreSQL, MySQL, and SQLite. Prioritizes future migration flexibility over DB-specific optimizations. Confidence: 0.9
- Wants modules built incrementally, step by step — start with SQL/migrations first, then progressively build other layers. Explicitly does NOT want all layers generated at once. Confidence: 0.95
- Provides reference code snippets (SQL, schemas) as "something like this" drafts rather than abstract specs — expects the assistant to use them as the foundation and build around them. Confidence: 0.8
- Requests explicit architecture/documentation guides (e.g. ARCHITECTURE_GUIDE.md) to maintain context across separate conversation sessions — values cross-conversation continuity via written reference documents. Confidence: 0.85
- Focus is on building reusable modules only; the assistant should NOT scaffold client systems (sistemas_clientes, specific apps). The user will compose final systems independently from the completed modules. Confidence: 0.9
- Expects accurate error/diagnostic reporting — does not accept "no errors found" when errors clearly exist; trusts IDE diagnostics as ground truth and gets frustrated by incorrect dismissals. Confidence: 0.85
- Delegates infrastructure execution to the assistant — expects the AI to run migrations, start servers, test endpoints, and fix issues directly, rather than being given commands to run manually. Confidence: 0.85
- For system-level troubleshooting (port conflicts, process management), wants to be shown the actual CLI commands (netstat, taskkill, etc.) so they can learn and run them independently, rather than having the assistant silently execute them. Prefers transparency and education for OS-level operations. Confidence: 0.85
- Wants unused/redundant code and files proactively deleted during integration or refactoring work — expects code hygiene, not just accumulation. Actively commands deletion of old directories/files when reorganizing to prevent confusion. Confidence: 0.85
- Prefers visual/interactive API testing tools (Swagger UI) over manual curl/CLI-based endpoint lists for testing and validating APIs. Confidence: 0.75
- Expects screens to have full CRUD functionality (create, read, update, delete) with interactive forms — not just read-only placeholder views. Treats any screen without CRUD as incomplete. Confidence: 0.85
- Wants input validation enforced on BOTH frontend and backend independently (defense-in-depth). Backend must reject invalid data even if frontend validation is bypassed (e.g. via curl). Fields like phone numbers must reject letters, emails must match format, names must be letters-only, etc. Confidence: 0.85
- Expects proper separation of concerns in Flutter frontend code: screens should ONLY handle layout/responsive composition, with business logic in controllers (ChangeNotifier), UI pieces extracted into reusable widgets, and actions/dialogs in separate files. Rejects monolithic screen files that mix everything together — considers it a bad practice. Confidence: 0.95
- When asked to make multiple items match a reference (e.g., "make all modules match module X's structure"), only modify the non-conforming targets — never destructively alter, restructure, or delete from the reference module itself. The reference is sacred; everything else adapts to it. Confidence: 0.9
- When evaluating or restructuring project architecture, prefers a conversation-first approach — discuss and align on strategy before generating any code. Explicitly signals this with requests like "hablemos no hagas codigo." Confidence: 0.9
- Strong aversion to duplicate or overlapping directory structures that serve the same purpose (e.g., lib/screens/ vs modulos_base/ vs modules/). Wants a single, unambiguous source-of-truth location for each file — no parallel trees that cause confusion about where code "really lives." Expects all project code to reside within `lib/` (the Flutter-standard boundary), not scattered in root-level directories like `modulos_base/` or `core/`. Confidence: 0.92
- Demands structural consistency across ALL modules — every module must follow the exact same internal directory layout convention (e.g., `frontend/screens/`, `frontend/controllers/`, not `frontend/src/screens/`). Notices and flags when any module deviates from the established pattern, even if it compiles correctly. Treats structural inconsistency across modules as a defect that must be fixed. Confidence: 0.88
- Expects the UI to look and work well on ALL screen sizes (mobile, tablet, desktop) — treats ANY overflow, even by a few pixels, as a critical bug, not a nice-to-have. Zero tolerance for RenderFlex overflow or layout assertion failures. When something looks broken on any screen size, expects the assistant to diagnose and fix ALL related responsive issues across the entire codebase, not just the single file mentioned. Explicitly demands full responsiveness ("DEBE SER RESPONSIVO TODA PANTALLA"). Confidence: 0.9
- Prefers desktop = data tables, mobile = card-based layouts for data lists. Rejects horizontal-scroll tables on mobile as ugly/illegible ("se ven horribles"). Wants all data tables across all modules converted to vertical card layouts when screen width < 700px, while keeping existing table format on desktop. Confidence: 0.9
- Wants bug fixes and non-trivial code changes explained verbally AND documented with inline comments in the code. Treats uncommented fixes as incomplete — asks "explícame cuál era el error y mejor si me lo comentas." Confidence: 0.85
- Infrastructure-averse: does not want to maintain 24/7 servers — has no dedicated computer and rejects paid cloud hosting. Prefers offline-first, self-contained solutions (e.g. signed license files, local verification) over server-dependent architectures. Wants systems that work without requiring always-on connectivity to any central server. Confidence: 0.9
- Wants systems to support dual deployment modes: Docker+PostgreSQL for clients needing multi-device server setups on PC, and SQLite-only for standalone mobile use without a server. Values deployment flexibility so each client can choose the mode that fits their needs. Expects a shared abstraction layer (e.g. IDatabase interface) so the same module code works transparently across both modes. Confidence: 0.85
- When presented with multiple solution alternatives (e.g. encrypted tokens, Bluetooth, QR, P2P, embedded keys), explicitly gravitates toward the simplest, most practical option — values implementation speed and simplicity over technological novelty. Dismissed "more modern" approaches in favor of basic key-based licensing because "son más rápidas." Confidence: 0.8
- Wants lightweight mobile-first admin/management interfaces for business operations — prefers a clean phone screen showing key data (clients, device counts, expiration dates) with simple action buttons (extend, verify) over complex web dashboards or CLI-based management tools. Confidence: 0.75
- Prefers fixing problems at their root source (e.g., backend/API) rather than applying workarounds at the consumer layer (e.g., frontend). When presented with a workaround, will push back and ask "¿no sería mejor modificar la API?" — considers backend-side fixes cleaner and more correct than defensive handling downstream. When a working fix is in place but a more architecturally clean solution exists (e.g., SQL-level `::float8` cast vs Dart-side `is String` checks), explicitly asks for "la mejor opcion posible" and expects the assistant to refactor toward the cleanest approach. Confidence: 0.9
- When a bug is found and fixed in one location, expects the assistant to proactively audit ALL similar locations in the codebase for the same issue and fix them systematically — not just the files explicitly mentioned. Wants confirmation that the fix was comprehensive (e.g., "¿pero no hacía con todos?"). Treats partial fixes as incomplete. Confidence: 0.85
- Prefers numbered page-index pagination (1, 2, 3...) with explicit page controls for data tables, rather than "load more" buttons or infinite scroll. Expects pagination to be applied uniformly across all data tables in the project. Confidence: 0.8
- Cross-browser compatibility is a non-negotiable requirement — the application must work on ANY browser without special flags or workarounds. Rejects solutions that only work in specific browsers (e.g., "use Chrome" or "add --web-renderer html flag"). Considers browser-specific solutions as incomplete. Confidence: 0.9
